# Auto-Save Daily View + Nightly Finalization — Design Spec

## Goal

Remove the "Complete Day" button (and Skip Day / Skip Morning with it) and replace the entire daily-dosing interaction model with: every checkbox saves live, individually, the instant it's tapped; the treatment position, Reaction Ramp steps, and day-completion status all finalize automatically overnight from a full replay of the day's actual data — not from a manual "I'm done" gesture.

## Motivation

A real production incident (2026-09-14) showed the current model's core flaw directly: two family members using the app around the same evening each independently pressed Complete Day from their own device's stale, un-synced local snapshot. Neither knew about the other's change. The result was two fragmented `dose_log` rows for the same real evening (one with morning items checked and evening items missing, one with only evening items) and the treatment position advancing twice for what was actually one calendar day's dosing — silently, with no error, no warning, and the earlier device's data effectively hidden by the later device's overwrite.

This is not a one-off bug to patch — it's the button model itself. Every incident this session in this area (a same-device double-tap advancing the position twice, a debounced save persisting a merely-viewed day as if it were live, a stale `is_skipped` flag surviving a correction) traces back to the same root shape: an imperative, single-shot action trusting a client-held snapshot with no server-side reconciliation against what's actually true. A two-parent household actively checking things off at overlapping times is normal, expected usage — not an edge case — so this needs an architecture where that usage pattern is safe by construction, not one more special case bolted onto the button.

## Architecture

**Two stores, everything else derived.** `dose_log.checked_foods` is the raw, live ground truth for what was actually checked, written directly and incrementally by every checkbox tap. `treatment_food_progress` is the ledger rollup, always fully recomputed from `dose_log` via the existing `recomputeFoodProgressFromHistory` replay (the same mechanism `DayEditor`'s trailing-edit save already trusts) — never advanced incrementally from a cached snapshot. Nothing else is separately stored.

**Buffer/7-day-rule and History's per-day icon are two consistent, correctly-scoped projections of the same rule — not two competing definitions.** Buffer math (`calculateBufferFromProgress`) reads `treatment_food_progress` directly, unchanged — a food's position only advances on a calendar day where its own `evening-<name>` key was checked (`advanceProgressForDay`'s existing rule). History's per-day calendar icon uses the existing `classifyDoseLogDay` (unchanged), which requires the *same* condition — every treatment food's `evening-<name>` key checked for that entry — before it can return `"complete"` or `"treatment-complete"` (it further distinguishes those two only by whether maintenance/meds were *also* fully checked that day, a detail irrelevant to buffer). So the buffer-relevant predicate from `classifyDoseLogDay`'s output is `status === "complete" || status === "treatment-complete"` (equivalently, `treatmentCheckedCount === treatmentKeys.length`) — not the literal string `"complete"` alone, which is over-strict for this purpose. Any future 7-day-minimum-rule display should derive from `treatment_food_progress`'s per-food history the same way buffer does, not from `classifyDoseLogDay`. Both code paths are independently correct and already verified to use the identical `evening-<name>`-checked-per-week-schedule key convention, so there is no drift risk between them despite being two separate functions — they answer different questions (current aggregate position vs. one specific day's classification) from the same ground truth, not the same question twice.

**Live per-key checkbox writes.** Every checkbox toggle (morning, evening treatment, medication) issues one atomic `INSERT ... ON CONFLICT (family_id, dose_date) WHERE session = 'day' DO UPDATE SET checked_foods = dose_log.checked_foods || excluded.checked_foods` — creating today's row on the first tap of the day, merging exactly one JSON key into it on every tap after. This is what makes concurrent edits from two devices safe: two people toggling *different* keys are two non-conflicting writes to the same row, serialized by Postgres itself, with no client-side read-then-write gap for a second write to race into. Two people toggling the *exact same* key within the same second is the one case where the later write simply wins for that key — an acceptable, expected outcome for any shared-state app, and far better than today's whole-object overwrite losing everything else on the row.

**Nightly finalization is the sole trigger for position/ramp advancement.** No button, no per-tap advancement. On every app load, before anything else renders, the app ensures a `dose_log` row exists for every calendar date from `cycle_start_date` through yesterday, bounded to the most recent 60 days exactly as today's lazy backfill already caps it (creating an empty/unchecked one for any date with zero taps — this generalizes today's lazy backfill, which already does exactly this for detected gaps, to run for *every* day rather than only when a gap is detected), then recomputes `treatment_food_progress` via a fresh, full `recomputeFoodProgressFromHistory` replay and Reaction Ramp step advancement via the same existing ramp-resolution functions, applied per day in chronological order. This recompute is **idempotent** — running it from two devices within seconds of each other produces the identical result both times, because it derives the answer fresh from the full ledger rather than incrementing a cached number. This is the property that actually closes the race: not by preventing concurrent execution, but by making concurrent execution harmless.

**Per-food blocking is preserved exactly, just relocated.** Today, `recomputeFoodProgressFromHistory` already advances each treatment food independently — a food only advances on a calendar day where its own `evening-<name>` checkbox was true. The Complete Day confirm dialog was always advisory on top of this; it never let an unchecked food fake-advance. Removing the button removes that advisory dialog, not the underlying rule — the rule was always enforced by the replay, which is unchanged.

**Header and per-food badges are unaffected.** `getGlobalPosition()` (the minimum position across foods) still drives the single header number; per-food badges (already built, Phase 3.5) still appear only when a food has diverged from that number. No new UI concept needed for foods that fall behind on different dates for different reasons — the existing badge mechanism already handles arbitrary per-food divergence correctly and unambiguously.

**The missed-dose safety net moves from a blocking dialog to an informational banner**, reusing the existing `BannerInfo` type and copy unchanged (`{kind: "single", date, foods}` / `{kind: "multi", count, startDate, endDate}`), now fired by the unified nightly finalization job instead of only legacy gap-detection. A morning open after a day finalized with an unchecked treatment food shows "\<date\> wasn't logged — \<foods\> weren't given," linking to History to correct it if it actually was given. No blocking, no confirmation required — Trailing Edit stays open for the entire current cycle regardless.

## Schema Changes

- **New column:** `dose_log.dose_date DATE NOT NULL` (for `session = 'day'` rows) — the row's real calendar-date identity. Replaces every existing "parse `completed_at`, apply the noon-UTC-anchor convention, hope the local timezone math is right" code path with a plain date comparison. This retires the "UTC vs. local timestamp mismatch" defect class recorded in the Carry Forward backlog as a side effect, not an extra task.
- **New constraint:** a partial unique index, `CREATE UNIQUE INDEX ... ON dose_log (family_id, dose_date) WHERE session = 'day'` (a plain `UNIQUE` table constraint can't carry a `WHERE` clause in Postgres) — enforces exactly one row per family per real calendar day, which is what makes the `ON CONFLICT` merge-write meaningful and gives it a target to conflict on.
- **`completed_at` is *not* repurposed.** It stays exactly what it is today — a timestamp set whenever a row is touched — but stops being read by any app-facing logic going forward. It's audit/ordering metadata only — see the Architecture section above for what buffer and day-status actually read instead, and why that's not a new drift risk.
- **Migration of existing rows:** every existing `dose_log` row needs a `dose_date` backfilled from its `completed_at`. This must replicate the exact same local-date derivation the app already uses today (`formatDateOnly(new Date(completedAt))`, which resolves in the *device's* local timezone) — a raw SQL timezone cast is not safe here, since it would silently reattribute some historical rows to the wrong calendar day if it doesn't match what was already shown to the family. This needs a one-time script using the same JS date logic already in `lib/schedule.ts`, run once. **Verification is not a generic spot-check — it must specifically cover the one production family with real history**, `00000000-0000-0000-0000-000000000001` ("Joshy"), whose `treatment_food_progress` position was already hand-corrected once this week via the Recompute Anchor Fix ticket's manual `UPDATE`. The implementation plan must include a concrete step: run the backfill script's date derivation against every one of this family's actual `dose_log` rows (the full Sept 2–14 history established and directly queried across this session) and diff the computed `dose_date` against the calendar date already known and confirmed correct for each row from this session's own investigation, before trusting the script against the rest of the table. A wrong backfill here would corrupt this specific family's live treatment record — the exact risk class this whole redesign exists to prevent, not a hypothetical.

## Removed Entirely

- The "Complete Day" button (`CTAButton` instance in `EveningSection.tsx`) and its handler chain (`onCompleteDayTap` → `handleCompleteDay` in `app/daily/page.tsx`).
- `CompleteDayConfirm.tsx` and the `showConfirm`/`handleCompleteDayTap`/`handleConfirm` logic wrapping it in `EveningSection.tsx`.
- Skip Day and Skip Morning: the "Skip morning" link in `EveningSection.tsx`, `onSkipMorning`/`handleSkipMorning` in `app/daily/page.tsx`, and `saveSkipMorning`/`saveSkipLog` in `lib/supabase.ts`. An unchecked box already means "not given" under the new model — no separate action needed to say so.
- The `completingDay`/`completingDayRef` re-entrancy guard added earlier this week — moot once there's no explicit action left to guard against being pressed twice.

## Testing

The pure-function core (`recomputeFoodProgressFromHistory`, `classifyDoseLogDay`, the nightly finalization's per-day iteration logic) stays fully covered by the existing Vitest suite, extended with new cases for: two same-day writes touching different keys merge correctly; a day finalizing with only some foods checked advances only those foods; multi-day-gap finalization on first load after several unopened days. The live per-key write path itself (the `ON CONFLICT` merge, concurrent from two simulated sessions) is exactly the class of behavior the existing pure-function suite can't reach — this is the component/integration-testing gap already flagged and greenlit as a separate backlog item (see BRIEF.md, "iOS App Store Publishing"). Recommend at minimum a targeted integration test against a real (or emulated) Postgres instance for the `ON CONFLICT` merge behavior specifically, even before the broader component-testing infrastructure is built out, given this is the exact mechanism the whole redesign's safety property rests on.

## Rollout

This changes core dosing-recording behavior for a real family actively using the app daily for a child's medical treatment. Per this project's standing rule, this is UI-facing and requires Project Owner sign-off regardless of QA/review status before merging to `main`. Given the severity of getting this wrong (silent data loss or incorrect position advancement, same class of risk as the incident that motivated this work), recommend building and testing this in an isolated worktree exactly as the Trailing Edit Redesign was, with a full whole-branch review before Project Owner review — not a direct-to-`main` build this time, given there's no equivalent time pressure forcing that shortcut.
